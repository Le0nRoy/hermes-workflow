# Hermes Workflow

## Назначение
Настройка и проверка Hermes + Hermes Kanban для фриланса по автоматизации API/UI-тестирования. Проект развивается параллельно Tortuga-AI; автоматическая замена существующей системы не предполагается.

## Контекст владельца
База знаний: `../second-brain/INDEX.md` относительно корня проекта; при другом размещении использовать указатель из памяти Hermes или согласованный SECOND_BRAIN_ROOT.
При вопросах о целях, бюджете, приоритетах и решениях открыть индекс, затем только необходимые документы. Обновление базы выполнять по её RULES.md. Не дублировать личный контекст в этом репозитории. Предложения агента не считать решениями владельца.

## Порядок работы
- В начале работы проверять git status; сохранять чужие изменения.
- Читать файлы перед изменением. Работать в feature-ветках, не коммитить напрямую в main.
- Перед настройкой Hermes загрузить скилл hermes-agent и необходимые справочные материалы; актуальные возможности проверять по официальной документации и установленной версии.
- Живую конфигурацию Hermes менять штатными командами, не ручным редактированием config.yaml.
- Отдельно согласовывать изменения действующих сервисов, других профилей, внешние публикации, деплой и доступы. Исследование не означает разрешение на внедрение.
- Не сохранять здесь пароли, токены, авторизационные файлы, сырые чаты, клиентские данные и runtime-базы Hermes. Шаблоны содержат только заполнители. Наличие .gitignore не заменяет проверку содержимого перед коммитом.
- Различать организационное разделение (профили, worktree) и реальную изоляцию файлов, процессов и учётных данных.
- Проверять изменения безопасными тестами и реальным выполнением. Bash-скрипты дополнительно проверять bash -n. Не выдавать заглушки и планы за работающую систему.
- В отчёте разделять выполненное, проверенное, предложения и блокировки. При нехватке существенной информации спрашивать владельца.

## Сравнение процессов
В первую очередь сравнивать собственные скиллы Tortuga-AI, make-feature и bulletproof как альтернативные процессы. Не объединять их автоматически в один конвейер. writing-plans, planning-tests и implementing-tasks не являются обязательной основой.

При адаптации Tortuga-скиллов явно распределять обязанности существующего runner: полный запуск тестов, публикация ветки, создание PR и восстановление. Не предполагать, что Hermes автоматически выполняет эти обязанности.

Фиксировать исходный commit, требования, версии скиллов и моделей, результаты проверок, расход доступных ресурсов и вмешательства человека. Отделять проверку надёжности инфраструктуры от сравнения методологий.
