# Кластеры работы: операторский чат → итерация → карточки

Статус: предложение для согласования, не launch gate и не календарное обещание. Основание: текущий чат и @session:default/20261015_173528_f876f0. Состояние карточек проверено при составлении; актуальные статусы всегда в Kanban.

## Минимальная модель
После завершения соседнего чата приоритет и правила уточнены: канонический первый пакет — [sprint-01.md](sprint-01.md), итоговая карточка `t_f53d9c4e`. Он ещё требует утверждения исполнения. Таблица H1–H7 ниже — прежняя тематическая дорожная карта, не альтернативный первый спринт и не разрешение запуска. Сначала safety-спринт, затем локальный сквозной проход и GitHub A/B. Локальный hermes-workflow не зависит от bridge.

Исполнимые спринты раздельны по проектным доскам: штатные cross-board dependencies не подтверждены и проверка в соседнем чате показала их отсутствие. Межпроектный обзор допустим, но не единый исполнимый DAG. Итог каждой доски — `[acceptance]` с prerequisites всех задач спринта. Реализация требует отдельного reviewer; после первого review максимум два цикла исправления/повторного review. Человек принимает итог спринта, а не каждую техническую задачу. Новые улучшения вне scope сначала предлагаются владельцу; автоматическое создание карточек не разрешено.

Один операторский чат ведёт одну активную итерацию. Состав — ссылки board/task, не копии карточек. Статусы только в Kanban. Файл итерации содержит ID, цель, session link, разрешения и критерий завершения; chat session ID записывать только после проверки. При новом чате обновлять связь, не терять историю.

Членство в итерации не создаёт prerequisite и не разрешает запуск. Не разблокировать набор целиком. Сейчас нет проверенного enforcement allowlist: todo/triage не гарантируют парковку. Начинать с одного writer на общий checkout; отдельный чат тоже writer. Не переключать global dispatcher в рамках планирования.
