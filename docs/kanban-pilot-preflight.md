## Что подтверждено установленным исходным кодом

Корень исходников: `${HERMES_HOME}/hermes-agent` (чтение, без правок).

- `hermes_cli/kanban_db_dispatch.py:1794–1802`: review_dispatch читается через load_config, по умолчанию true. Здесь нет аргумента board. Менять эту настройку как якобы локальную для одной карточки нельзя.
- `gateway/kanban_watchers_dispatcher.py:34–117`: dispatch settings читаются при старте; для применения нужен restart. Null max_in_progress разрешается через memory-derived default, а не через обязательную сериализацию. Конфигурация относится к dispatcher, не является отдельной настройкой нашей карточки.
- `hermes_cli/kanban_db_dispatch.py:649–740`: timeout завершает worker и возвращает карточку в retry phase, если circuit breaker не остановил её. Сам `max_runtime_seconds=1800` не обеспечивает «только ручной повтор».
- `hermes_cli/kanban_db_dispatch.py:1572–1583`: после rate_limited и cooldown разрешается повтор; комментарий прямо описывает повторение до восстановления квоты. Это противоречит требуемой ручной остановке на квоте. Изменение failure_limit само по себе не решает этот путь.
- `hermes_cli/kanban_db_dispatch.py:2743–2777`: штатная сборка команды worker не добавляет `--max-turns`. CLI `hermes chat --help` действительно предоставляет `--max-turns N`, но его наличие у ручного запуска не доказывает per-task enforcement у dispatcher. Goal-loop budget не подменяет число итераций агента.

## Решения, необходимые для продолжения

Не нужно повторно подтверждать одну очередь, default, pool и временные пределы A1-1…A1-5. Необходимо закрыть только остаточные вопросы:

1. Pool: подтвердить допустимый upstream, отсутствие дополнительных списаний/платного fallback (включая auxiliary calls), выделенную квоту и разрешённый источник её проверки. Секреты не присылать. Текущий работающий чат не доказывает эти условия.
2. Scope настройки: разрешить конкретную доработку/лабораторную проверку механизма «manual-only retry и human-only acceptance». Прямой путь через default-конфигурацию затрагивает dispatcher и может требовать gateway restart; таких разрешений нет. Не применять глобальные изменения под видом board-local. Вариант отдельного ручного режима требует согласования и доказательства отсутствия гонки со штатным dispatcher; это не готовое решение.
3. Разрешить первый локальный коммит после проверки состава, без push, и применимую часть протокола A1.1-6/P01–P07 перед пилотом. Без этого воспроизводимый baseline и согласованный протокол отсутствуют.

Предлагаемая учебная цель после снятия gates: локальная HTTP API fixture с позитивными/негативными проверками, известным дефектом и исправлением, без внешних сервисов/клиентских данных/новых зависимостей. Это предложение, не выполненная задача. Требования, ожидаемый набор тестов и timeout фиксируются до запуска; результаты не выдумываются. Долгие тесты и security/backup испытания остаются отдельно согласуемыми.

## Восстановление и безопасное продолжение

В этой попытке живые config, БД напрямую, профили, сервисы и Tortuga-AI не изменялись. Откат конфигурации после этой попытки не требуется. Не выполнять reset/clean или откат общего дерева: исходные файлы untracked и могут принадлежать другим задачам.

Перед будущей разрешённой настройкой:

1. Зафиксировать точные затрагиваемые ключи, значения и факт присутствия ключа, scope и план restart. `hermes config get` возвращает resolved value и один не доказывает наличие явного ключа.
2. Применять только штатный `hermes config set KEY VALUE`; для восстановления отсутствовавшего ключа — `hermes config unset KEY`, а не запись null. Синтаксис set/unset проверен через `--help`, сами операции не выполнялись.
3. Возвращать только собственные изменения, не перетирать параллельные правки; при расхождении остановиться. Restart только в согласованном окне.
4. Повторно проверить exact keys, состояние сервисов и контролируемый запуск. Изменение конфигурации не означает изменение уже запущенного worker.
5. Не восстанавливать live Kanban DB из непроверенной копии. Backup/restore со SQLite WAL и выбор хранилища требуют отдельного разрешения, здесь не выполнены.

Это ограниченный runbook для будущей настройки, а не проверенное disaster recovery. API/UI-тестов, caps fixtures, quota probes, резервного копирования и человеческой приёмки результата не было. Расход квоты неизвестен, не равен нулю. Задачу нельзя отметить done или отправить в auto-review как будто реализация закончена; требуется needs_input по указанным предусловиям.
