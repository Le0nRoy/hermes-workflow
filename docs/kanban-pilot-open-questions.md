## Q1. Условия и квота pool

Как подтвердить, кто фактически обслуживает запросы, из чего оплачиваются основные и вспомогательные вызовы и сколько ресурса выделено пилоту?

- A — владелец сообщает допустимый upstream, подтверждает отсутствие дополнительных списаний и платного fallback, указывает выделенную квоту с единицами/периодом и источник проверки остатка.
- B — условия пока неизвестны; разрешить только read-only проверку конкретного несекретного источника, указав его путь или URL. До результата автоматический пилот не запускать. Рекомендуется, если нет достоверных сведений.
- C — отложить пилот до восстановления/уточнения квоты.

Для A/B нужны фактические сведения или источник, одной буквы недостаточно. Пароли, токены и auth-файлы не присылать. Работающий чат не доказывает ни остаток квоты, ни отсутствие списаний.

## Q2. Где разрабатывать остановку повторов и человеческую приёмку?

Предыдущий preflight обнаружил автоматические повторы после rate limit и глобальный scope части настроек. В прочитанной истории этой карточки также есть rate_limited → ready → spawned. Простая смена failure_limit не доказана как решение.

- A — сначала подготовить локальную лабораторную реализацию и точный протокол проверки без изменения живого default, установленного Hermes и рабочих сервисов. Тестовая БД не должна попадать под рабочий dispatcher; отсутствие гонки нужно доказать до запуска. Подключение к живому контуру — отдельное согласование. Рекомендуется.
- B — подготовить перечень конкретных изменений живого default/dispatcher, оценку влияния, откат и окно restart; предъявить на отдельное утверждение до применения. Выбор B сам по себе не разрешает restart или правки.
- C — не менять автоматизацию; подготовить вариант ручного пилота с сохранением результатов в Kanban. Запуск только после проверки, что рабочий dispatcher не запустит ту же работу параллельно.

Ни один вариант не отменяет согласованных лимитов и не объявляет механизм уже работающим. Нужны проверки остановки на квоте/timeout, запрета автоматического повторного запуска и ожидания именно человека.

## Q4. Учебная цель и протокол

- A — согласовать как план P01–P07 из A1.3 и последующую человеческую приёмку P12 для локальной HTTP API fixture: позитивные/негативные тесты, известный дефект, исправление, повторный полный прогон. Только учебные данные, без внешнего API, новых зависимостей и клиентских материалов. Перед исполнением зафиксировать точные сценарии/число тестов, timeout, окно наблюдения human gate и допуски caps; запуск после закрытия Q1–Q3 и согласования этих чисел. Рекомендуется.

- C — пока согласовать только детализацию протокола, без исполнения пилота.

P08–P11 (security, recovery, backup, ресурсы/расход) не получают разрешения на инфраструктурные действия этим ответом. Обязательная проверка оплаты/квоты перед запуском сохраняется. Длительные тесты сверх 1800 секунд, нагрузочные тесты, новый sandbox и backup требуют отдельного scope.
