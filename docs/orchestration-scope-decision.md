# Подтверждение архитектуры и разделение контуров

Источник: владелец в текущем операторском чате, после рассмотрения docs/github-hermes-orchestration-design.md. Архитектура подтверждена; это не разрешение на live rollout.

## Принято
Детерминированный integration service + adapter к native Hermes Kanban. Не строить второй worker dispatcher/retry loop. Плагин не обязателен для первого этапа; упаковку конфигурационного проекта как plugin решить позже.

## Два разных контура

### GitHub A/B: Tortuga-AI
Кандидат первого GitHub-пилота, поскольку разработка идёт постоянно. Явный agent:hermes вместе с поддерживаемой action-командой выбирает Hermes; без selector — обычный Tortuga-AI. Общий routing/ownership contract из исследования сохраняется. Состав конкретных пилотных issues и разрешение на live запуск ещё не утверждены.

### Локальный Hermes-native: hermes-workflow
`${HERMES_WORKFLOW_ROOT}` — конфигурации и средства восстановления Hermes после чистой установки. У проекта уже есть локальный Git и backlog Kanban; GitHub remote пока нет со слов владельца. Весь этот backlog исполняется исключительно Hermes, без agent-bridge/Tortuga-AI. Не требовать GitHub labels или создания remote для выполнения локальных карточек. Интеграционный adapter не является обязательной зависимостью этого контура. Требования isolation/admission/stop/recovery остаются и для него.

## Ещё не принято / не выполнено
- Упаковка проекта как plugin, создание GitHub репозитория и публикация.
- Конкретный live пилот, новые доступы и запуск сервисов.
- Полный GitHub App repository inventory: исследование не установило полноту.
- Итоговая внутренняя оркестрация Hermes, iteration gate и связь чат→итерация: работа продолжается в @session:default/20261015_173528_f876f0. Загрузить финальные решения только после сигнала владельца и согласовать их с этим контрактом; промежуточную модель не считать окончательной.
