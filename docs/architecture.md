## 2. Уже подтверждённые границы

Следующие ограничения заданы владельцем в AGENTS.md, карточке и базе решений; это не утверждение предлагаемой реализации:

- Hermes развивается параллельно Tortuga-AI, без автоматической замены.
- Tortuga-скиллы, make-feature и bulletproof сравниваются как альтернативы, не обязательные последовательные стадии.
- Сервисы, другие профили, доступы, внешняя переписка, публикации, деплой и новые расходы требуют отдельного согласования.
- Не вводить две обязательные очереди одной работы; секреты, runtime-БД, сырые чаты и клиентские материалы не хранить в репозитории.
- До подтверждения архитектуры не начинать её настройку. Допуск клиентских данных — отдельная проверка, не следствие успешного учебного пилота.

## 3. Предлагаемый минимальный контур

Владелец задаёт требования и разрешённые действия → одна карточка Kanban → один исполнитель → детерминированные проверки → независимая проверка владельцем → зафиксированный результат.

### Роли, а не обязательный набор профилей

| Роль | Ответственность | Реализация пилота (предложение) |
|---|---|---|
| Владелец | Объём, разрешение запуска, маршрут модели, бюджет, риск, окончательная приёмка | Человек; согласования в комментарии карточки с указанием редакции документа |
| Исполнитель | Изменения внутри разрешённой области, полные тесты, сохранение результатов и ограничений | Один worker существующего `default`, без новых профилей и вложенных агентов |
| Проверяющий | Сверка требований с diff и результатами, повтор проверок, решение о приёмке | Владелец; новая независимая агентная сессия только по отдельному разрешению |
| Диспетчер | Claim, запуск, heartbeat/reclaim, маршрутизация состояния | Существующий механизм Hermes; не запускать второй dispatcher |
| Детерминированный runner | Запуск тестов, timeout, exit codes, отчёты | Команды проекта/будущий скрипт, не LLM-оценка «всё зелёное» |

`default` — организационный исполнитель, не отдельная учётная запись ОС и не security sandbox. Специализированные профили добавлять лишь при доказанной необходимости и после разрешения; одинаковый профиль в разных сессиях не означает независимость полномочий.

### Единственный источник состояния

- Kanban хранит живые статусы, зависимости, согласования и handoff. Использовать инструменты `kanban_*`; не править SQLite вручную.
- Git хранит исходники, проверяемую архитектуру и безопасные скрипты. `docs/kanban-tasks.json` остаётся manifest ID/связей, не зеркалом статусов.
- Результаты тестов и версии запусков — в `experiments/<task-id>/<run-id>/` с ссылкой из карточки. Это свидетельства выполнения, не очередь.
- Tortuga-AI сохраняет свою отдельную работу. Для эксперимента выбирается один владелец состояния: Hermes-карточка не должна одновременно автоматически исполняться runner Tortuga. Ссылка на внешний issue допустима, двусторонняя обязательная синхронизация статусов не нужна.
- Сессия/чат и память агента не заменяют карточку. Непроверенные слова предыдущего worker не равны выполненным тестам.

| Вид состояния | Авторитетный источник | Граница ответственности |
|---|---|---|
| Правила и разрешённый scope | AGENTS.md + тело карточки + явные решения владельца | Архитектурное предложение не расширяет разрешения |
| Решения владельца | Исходный комментарий выбранной доски; раздел 9 — его проверяемая проекция | Дата, автор, точный ID решения; база знаний обновляется отдельно по её RULES.md |
| Жизненный цикл и зависимости | Live `kanban_show` выбранной доски, events/runs | README и manifest не зеркалируют статусы |
| Исходники и baseline | Рабочее дерево и Git HEAD | Сейчас HEAD отсутствует; текст handoff его не заменяет |
| Конфигурация и действующие права | Целевые live CLI/OS проверки из фактического worker | Аудиты содержат только датированные снимки |
| Результаты и расход запуска | Команды, exit codes, машинные отчёты, разрешённая телеметрия с run ID | Отсутствующий расход помечать unknown; подписка не равна нулевому расходу квоты |
| Тариф и доступная квота | Условия провайдера и разрешённый dashboard/подтверждение владельца | Имя `pool` или модели не доказывает источник оплаты |
| Контекст и долгосрочные цели | Второй мозг по INDEX.md | Не дополнительная очередь исполнения |

Статус детализации источников: предложение в рамках подтверждённого A1-1; основание — устранить расхождения между снимками и live state. Вопрос владельцу: есть ли возражения против этой карты без обязательной синхронизации со второй очередью? До ответа она не расширяет существующие права.

### Lifecycle и согласования

Пилотная работа использует одну карточку. После выполнения исполнитель запрашивает человеческую приёмку, но не считает это разрешением на публикацию. Технический механизм human-only review должен быть проверен в настройке: по аудиту `review_dispatch=true`, поэтому обычный перевод в review может запустить автоматического reviewer. Не переводить туда карточку в расчёте на ожидание человека без проверки маршрутизации. Глобально отключать review-dispatch ради одной доски без оценки влияния нельзя.

Для текущей архитектурной карточки отсутствие выбора владельца — `needs_input`, не «готово». После явного подтверждения записать решения в раздел 9, выполнить `kanban_complete` с handoff: это снимает зависимость у существующих дочерних карточек. Не создавать параллельную карточку review архитектуры и не разблокировать весь backlog. Дочерняя `t_210125a5` проверяет клиентскую безопасность позже, а не утверждает архитектуру вместо владельца.

Для `t_2fab5f0a` полученные ответы фиксируются без расширения смысла; завершение документальной фазы передаёт проект и остаточные вопросы существующей дочерней `t_93841548` для итоговой сверки. Это не окончательная приёмка реализации и не автоматическое разрешение всего backlog. Отдельный same-card review не создаётся. Внешняя переписка не инициируется; допустим текущий thread Kanban/ответ владельца через Desktop.

Целевой переход одной пилотной работы: разрешённый scope → готовность после зависимостей → claim/run → команды и отчёты → человеческая приёмка → done. При отказе проверок — ограниченная доработка в той же карточке; при неизвестном разрешении/квоте — ожидание владельца. Автопереход по графу не является human gate. Для автоматического исполнения сначала доказать, что ожидание человека не запускает reviewer/auto-decomposer; иначе unattended-запуск запрещён предложением A1-3/A1-5.

## 4. Рабочие области и хранение

Подтверждённый вариант для начала: последовательная работа в существующем `dir` только с учебными/публичными данными; один writer во всей общей директории, включая интерактивные сессии. Владелец требует worktrees при параллельных фичах и допускает их раньше, если проще. Сейчас HEAD отсутствует, поэтому для документальной задачи сохранён общий dir и немагистральная ветка `chore/bootstrap`, без переключения общей директории. Проверка `git status` до и после обязательна. Не удалять чужие untracked-файлы, не выполнять reset/clean.

До воспроизводимого кодового эксперимента нужен отдельно разрешённый исходный Git-коммит после проверки состава файлов. Предложение: согласовать первый локальный коммит без push; зафиксировать его SHA. До такого разрешения коммит не делать, а полноценное сравнение из одинакового revision считать заблокированным.

Для последующего параллелизма: отдельный worktree и ветка на задачу, общий проверенный baseline. Worktree разделяет редактируемые деревья, но разделяет с основным репозиторием Git-объекты и доступы; не даёт запрета читать соседние файлы. Переход на worktrees — не условие для написания этого документа и не выполненная операция.

Живые настройки, auth и БД остаются вне Git. Board backup планировать отдельно: согласованный защищённый каталог вне репозитория, SQLite-consistent backup и restore в отдельную тестовую БД, никогда поверх живой. Конкретное хранилище/retention ещё не выбрано; наличие backup не заявляется. Нельзя просто копировать работающий файл SQLite и игнорировать WAL.

## 5. Права и границы безопасности

| Область | Предлагаемое правило пилота | Что обеспечено сейчас |
|---|---|---|
| Файлы | Запись только workspace и явно разрешённых временных артефактов | Ограничение задачи; `local` с общим UID не обеспечивает запрет ОС |
| Секреты | Не читать/копировать credential stores; только штатный ввод/хранилище при отдельном согласовании | Аудит 2026-10-15 подтвердил same-UID читаемость auth store по правам, не чтением содержимого |
| Shell | Без sudo, установки пакетов в систему, использования Docker socket для пилота и управления рабочими сервисами | Rootful Docker API реально доступен по аудиту; запрет организационный. Prompt/approval не равны изоляции; policy `deny` не ослаблять |
| Сеть | Только согласованный model route, документация и учебная цель | Allowlist не проверен и не применён |
| Публикация | Local-only; без commit/push/PR/деплоя, кроме явно разрешённого первого локального коммита | Контракт текущей карточки local-only; сам по себе не блокирует shell-сеть |
| Клиентские данные | Не допускаются до отдельной проверки | Изоляция и условия передачи провайдерам не подтверждены |

Профиль, board и worktree — организационные границы. Документированная маршрутизация инструментов по board не препятствует произвольному shell-доступу того же UID к чужим файлам или БД.

Целевой security boundary для клиентской работы выбирается после отдельного обследования: отдельный OS user либо правильно ограниченный container/VM, минимальные mounts, отсутствие домашнего каталога/SSH keys/Docker socket, минимальные credentials, сетевые ограничения и ресурсные лимиты. Контейнер с host home или privileged/socket-доступом не считать изоляцией. Подтверждать отрицательными проверками доступа с тестовыми canary-файлами, а не настоящими секретами. Эта карточка ничего из перечисленного не разворачивает.

## 6. Модель, лимиты и остановка

### Выбор маршрута — обязателен до настройки

Владелец выбрал существующий `pool` (A1-2). Предыдущая рекомендация прямого `openai-codex` больше не является выбранным вариантом. Выбор не доказывает upstream, условия подписки, доступную квоту и отсутствие платных путей: это отдельные предусловия запуска. Переключений в этой задаче нет. По возможности задавать маршрут на уровне запуска, без глобальной замены default; поддержку параметров проверить перед применением.

Альтернативы при новом согласовании: прямой `openai-codex` или официальный CLI с ручным запуском и фиксацией результата в той же карточке. Самостоятельно менять выбранный pool нельзя. Claude-подписка не считается автоматически доступной Hermes: ограничения подробно приведены в аудите. OAuth credentials не извлекать в сторонние инструменты. Никакой платный API fallback без отдельного согласования.

### Временно согласованные начальные пределы A1-3 (не применены)

| Предел | Предложение | Как проверять при реализации |
|---|---|---|
| Активные workers пилота | 1; вложенные агенты и параллельные writers выключены организационно | Один одобренный запуск; проверить фактические процессы и область действия dispatch cap |
| Время одной попытки | `max_runtime_seconds=1800` | На безопасном fixture проверить timeout и сохранение частичного результата |
| Итерации | 50 на попытку вместо наблюдаемых 150 | Проверить поддержку run-scoped настройки; не менять глобальный default без согласия |
| Повторы | Не более одной ручной повторной попытки после устранения причины | Проверить runtime retry/reclaim/goal-loop; не считать `failure_limit` универсальным лимитом всех повторов |
| Новые расходы | 0 без отдельного разрешения; без автоматического перехода на платный API | Владелец подтверждает тариф/credits и разрешённый маршрут, включая auxiliary calls |
| Квота | Проверить до старта и после; при отсутствии сведений не заявлять остаток | Dashboard/разрешённая телеметрия; не обещать hard token cap, которого не проверили |
| Heartbeat | Каждые несколько минут долгой работы | События карточки; heartbeat не заменяет прогресс или runtime limit |

Указанные cap — желаемый контракт, не существующая гарантия. `max_in_progress` может действовать шире одной доски; до изменения выяснить влияние на другие работы. Если безопасный локальный scope недоступен, оставить только один вручную одобренный запуск и не объявлять автоматическую сериализацию обеспеченной. До проверки enforcement не включать unattended-пилот.

Оговорка владельца A1-3: продумать долгие автотесты, чтобы не выйти за временную квоту. Пока лимит 1800 секунд не отменён. Предложение для `t_292e9717`, не реализованное здесь: отделить короткую агентную подготовку/анализ от детерминированного запуска набора тестов с собственным timeout, журналом, exit code и устойчивым ID; не тратить LLM-вызовы на опрос ожидания. Выживание runner после завершения worker, отмена, лимиты CPU/RAM/disk и доставка результата должны быть отдельно проверены. Background сам по себе не гарантирует долговечность и не разрешает обход cap; до согласования механизма длинные наборы не запускать. Наблюдаемые rate_limited/requeued этой карточки показывают, что требование остановки на квоте пока не обеспечено, а не что владелец разрешил неограниченные повторы.

CPU/RAM/disk: численные hard caps пока не выбраны и не применены. Для первой локальной API/UI-пробы предлагается сначала измерить ресурсы одной fixture, затем согласовать лимит памяти, CPU, диска и запас для действующих сервисов; без этого не запускать нагрузочные тесты и параллельные браузеры. Использовать существующий мониторинг при подтверждении его покрытия, не разворачивать второй обязательный dashboard. Основание — общий рабочий хост, не выделенная лаборатория. Статус: предложение A1.1, вопрос владельцу в разделе 9. Отсутствующий hard cap явно сохраняется ограничением даже при согласованном timeout.

Стоп: неизвестный платный маршрут, quota/429, отсутствие credentials, запрещённая операция, опасный diff, утечка данных, повтор одной и той же неисправности, выход за runtime. Сохранить безопасный handoff; не обходить deny и не переключать провайдера скрытно. Исчерпание квоты не лечить бесконечным retry; возобновление после восстановления — отдельное подтверждение в пилоте.

Перед адаптацией Tortuga runner обязанности фиксируются явно: полные тесты запускает исполнитель через детерминированные команды; проверяющий повторяет существенные проверки; commit/push/PR выполняются только после отдельного разрешения и проверки состояния; retries/recovery принадлежат настроенному диспетчеру/оператору, а не подразумеваются текстом скилла. В пилоте push/PR исключены, а не «автоматически обслуживаются Hermes».

Handoff должен содержать task/run ID, revision, команды и exit codes, артефакты, найденные ограничения, вмешательства человека, доступные показатели расхода (неизвестные не выдумывать). Метрики позже интегрировать с существующим мониторингом, без нового обязательного трекера. Инфраструктурные испытания отделены от сравнения качества скиллов.
