## Минимальные точки подключения (предложение, не решение)

1. Повторно использовать текущие Grafana/Prometheus/Alertmanager, а не ставить второй стек. Node exporter уже даёт общие CPU/RAM/disk; cAdvisor — контейнеры Tortuga. Для процессов Hermes на хосте отдельной метрики UID/service **не обнаружено** в просмотренных правилах/panels/scrape jobs; если нужна детализация Hermes, спроектировать низкокардинальный collector/exporter только для Hermes, без Docker socket и секретов. На стороне Prometheus понадобится одобренный scrape target, в Grafana — отдельный раздел существующей панели или новая небольшая панель в той же инсталляции. Не путать `agent_*` Tortuga с Kanban runs.
2. Каталог сигналов Hermes (отдельная карточка `t_14fe47a5`) должен сначала подтвердить источник, семантику и способы безопасного чтения status/reason/updated_at для tasks/runs. Только после этого обсуждать gauges по состояниям, counters переходов и age/heartbeat; штатный blocked отличать от зависания. Для отсутствующей телеметрии нужен явный «unknown/stale», а не нулевой успех. Логические причины ошибок классифицировать ограниченным набором, без текстовых error messages как labels. Проверенные затраты отдельно от непроверенных: LiteLLM spend нельзя автоматически приписывать Hermes.
3. Новые alert rules сначала локально валидировать и проиграть на обезличенных данных; избегать дубликатов Grafana/Prometheus и доставки в Telegram до отдельного разрешения. Учитывать отсутствие метрик, stale exporter и плановую блокировку как разные состояния. Любые изменения живых compose/Prometheus/Grafana, сетевых прав, профилей, деплой и отправка сообщений — отдельное согласование владельца. Потомок `t_2569a694` помечен triage и явно требует решения владельца до внедрения.
