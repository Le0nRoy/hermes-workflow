## Предлагаемый минимальный lifecycle (не применён)

1. **Постановка/допуск:** одна карточка с scope, учебными данными, ожидаемыми позитивными/негативными API/UI-проверками, известным дефектом, лимитами, путями и запретами. Владелец явно утверждает конкретную редакцию, model route/квоту и запуск. Не делать готовую к dispatch карточку до gate; обычное завершение родителя или разблокировка не равны человеческому разрешению.
2. **Готово → running:** только после закрытия зависимостей и gate, один исполнитель default, один writer в общем dir, без вложенных агентов; закрепить исходный revision (сейчас HEAD отсутствует). Dispatcher claim/run/heartbeat записываются в Kanban. Пределы из A1-3: 1800 секунд и 50 turns на попытку, не более одного *ручного* повтора после анализа причины — пока это требуемый контракт, а не обеспеченный механизм. При quota/unknown billing не стартовать; после timeout/rate_limited не принимать автоматический requeue за разрешение повторить.
3. **Проверка:** детерминированный полный набор тестов, точное число и IDs, exit codes, отрицательные проверки, дефектная/исправленная версия, diff и секрет-скан только собственных артефактов. Передать task/run ID, версию модели/скиллов, ресурсы и вмешательства человека. Отсутствующие показатели квоты пометить unknown. Исполнитель не выставляет себе приёмку.
4. **Приёмка владельцем:** отдельное явное решение по конкретным результатам: принято → done; замечания → доработка в той же карточке с новым bounded run только после разрешения; нехватка решения → ожидание человека, недоступный ресурс/квота → blocked. Проверить, что переход в review не вызывает auto-review: сегодня `review_dispatch=true`; как human-only gate он не принят. Нельзя использовать блокировку, которая автоматически перерастает в decomposition/ready, как доказанное ожидание человека. Испытать gate на отдельной безопасной лабораторной доске до unattended-работы.

Kanban — единый источник текущих статусов и решений; Git — исходники и безопасные отчёты; Tortuga-AI не получает вторую обязательную очередь для этой же работы. README описывает первоначальный каркас, а не live-состояние. Одобренные A1-1…A1-5 перечислены в `docs/architecture.md:181–203`; это не согласие с последующими деталями A1.1-6/P01–P12 и не принятие работающей системы.

## Изменения, риски, резервирование

Перед настройкой нужны: (a) подтверждённые допустимый upstream и источник остатка/тарифа pool, без платного fallback и новой услуги; (b) согласованная реализация и лабораторное испытание human-only gate и manual-only retry, причём возможные глобальные изменения конфигурации/default/gateway и окно restart согласовываются отдельно; (c) первый локальный коммит и проверенный состав файлов для baseline — только после отдельного разрешения; (d) применимая часть протокола P01–P07 и точные численные критерии, включая timeout проверок. Сейчас глобальный cap может затронуть другие boards; включать его как board-local нельзя. Предложение предпочтительно сначала реализовать и проверить отдельную лабораторию вне живого dispatcher/БД, затем принести точный change plan с rollback. Не менять установленный Hermes и не ручным редактированием config.yaml: штатные `hermes config set/get/unset` только после разрешения. Длинные тесты — отдельный детерминированный runner с собственными timeout/ресурсами и наблюдаемым результатом, не обход 1800 секунд через background.

Риск совместного UID и rootful Docker не снимается ни одной настройкой Kanban. Для клиентских данных потребуется отдельный UID или правильно ограниченная VM/container без host home/Docker socket с canary-проверками отказа; это вне текущего пилота. Параллельные фичи требуют согласованного Git baseline и worktrees, но worktree не создаёт security boundary. Другие профили, действующие сервисы, доступы, внешний обмен, публикации и деплой — только по отдельному согласию. До конца октября 2026 ориентир — существующие подписки Claude/ChatGPT; совместимость выбранного pool с ними и нулевая доплата не подтверждены.

**Предлагаемое backup/restore для согласования, не выполнено:** владелец выбирает защищённое хранилище вне репозитория и retention; в согласованном окне снять SQLite-consistent online snapshot живой доски (`sqlite3` `.backup` либо SQLite backup API, с учётом WAL), отдельно сохранить необходимый каталог вложений и проверить доступы/manifest без секретов в отчёте. Restore проводить **только** в отдельную тестовую БД/доску без активного dispatcher на этой копии: `PRAGMA integrity_check`, сверка известных ID, связей и attachments; затем документировать действия на случай отката собственных изменённых настроек (исходное presence/value каждого ключа, `hermes config unset` для изначально отсутствовавшего ключа). Не подменять живую БД копией без решения владельца; прямое копирование файла работающей SQLite БД ненадёжно при WAL. Название backup-каталога или Git не является доказательством наличия проверенной резервной копии. В этой задаче конфигурация не изменялась — откат не требуется.
