# Источники и семантика метрик Hermes (исследование, без подключения)

Проверено read-only на primary-host для установленного Hermes `v0.21.6+730.g97a9ae8`, исходник `${HERMES_HOME}/hermes-agent` (commit `97a9ae8ee5`), доска `hermes-workflow`, 2026-10-16. Это каталог для будущего адаптера, не обещание действующего мониторинга. Канонический источник состояния задач — Kanban; Grafana/панели не становятся второй очередью. Перед использованием перепроверить схему и политику доступа после обновления версии. Проектный бюджетный ориентир — существующие подписки до конца октября 2026, не гарантия бесплатного API и не разрешение подключать платные сервисы.

## Доказательства и способы безопасной проверки

- Установленная схема: `hermes_cli/kanban_db.py:795-959` (`tasks`, `task_links`, `task_events`, `task_runs`); типизация блокировки `:3143-3259`, возраст карточки `:4194-4204`. CLI `hermes kanban --help` предлагает `show`, `runs`, `stats`, `diagnostics`, `watch`. Статусы и граф см. также [официальный справочник](https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban). Чтение через `kanban_show`/CLI предпочтительно для ручной диагностики; внешний скрейпер обязан работать с read-only snapshot и явной версией схемы.
- Установленная схема сессий: `hermes_state_common.py:400-502` (`sessions`, `session_model_usage`); учёт вызовов `hermes_state_usage.py:275-391`, overview `agent/insights.py:270-316`; нормализация токенов/маршрута `agent/usage_pricing.py:610-680`, запись вызовов `agent/turn_usage.py:225-275`. Actual cost поля существуют, но это не доказательство записи счета провайдера.
- Read-only запрос `sqlite3 'file:${HERMES_HOME}/kanban/boards/hermes-workflow/kanban.db?mode=ro' ...`: 55 задач, 267 запусков, 7352 события на момент среза; 245 запусков имели outcome `rate_limited`. В `file:${HERMES_HOME}/state.db?mode=ro`: 284 сессии, 85 строк model usage; 266 сессий с `source=kanban`. Это диагностический снимок, не baseline для алертов; не копировать БД или тексты событий в Git. Для 55 карточек `tasks.session_id` был NULL, поэтому соединение run → session по этому полю нельзя считать достоверной атрибуцией. Сопоставлять только после отдельно проверенного стабильного ключа run/session и политики его доступности.
- Пример нужной формы агрегирования (только для локальной проверки на разрешённой копии, без сырых полей): `SELECT status, COALESCE(block_kind,'none'), COUNT(*) FROM tasks GROUP BY status,block_kind;` и `SELECT COALESCE(outcome,'active'), COUNT(*) FROM task_runs GROUP BY outcome;`. Запуск на живой БД строго `mode=ro`, не вызывать `connect()` Hermes, способный выполнять миграции. SQL не экспортировать с текстами `body`, `payload`, `error`, `summary` или с `session_id`.

## Минимальный каталог сигналов

`P` — период получения в проектируемом адаптере, не встроенная частота Hermes. `Проверка` — минимальный безопасный тест доступности. Метки разрешены только из заранее перечисленных категорий; `task_id`, PID, имя файла, текст причины, model/base_url, session ID и client ID — только в защищённой детализации, не в метриках. Каждый ряд должен включать собственный `collected_at`/признак свежести и состояние `unknown` при ошибке чтения.

| Сигнал / тип, единица | Источник и семантика | P / метки | Доступность / проверка |
|---|---|---|---|
| `hermes_tasks` gauge, задач | `tasks.status`: текущее распределение (`triage`, `todo`, `ready`, `running`, `blocked`, `review`, `done`, `archived`; возможен `scheduled` в текущем CLI). `todo` с открытым родителем — ожидание зависимости, не сбой; `triage` не обязательно авария. | 60 с; `status`, `board` из allowlist | Есть на доске; сверить сумму групп с числом `tasks` на одном snapshot. |
| `hermes_waiting_tasks` gauge, задач | `tasks` + `task_links`/статусы родителей + `block_kind`: `dependency_wait`, `owner_gate` (`blocked` + `needs_input` или явный комментарий владельца, классификация текстовой причины вручную), `capability`, `transient`, `unknown`. `block_kind` сохраняется после unblock: фильтровать по текущему status и событиям; нельзя трактовать старый kind на `running` как нынешнюю блокировку. | 60 с; `reason_class` (закрытый словарь), `board` | Частично: dependency и typed block доступны; свободный текст human gate не классифицировать автоматически. Проверить `kanban_show` на одной разрешённой карточке и графе родителей. |
| `hermes_run_outcomes_total` counter-by-snapshot, запусков | Агрегат всех исторических `task_runs.outcome` (`completed`, `blocked`, `crashed`, `timed_out`, `spawn_failed`, `gave_up`, `reclaimed`, `rate_limited` и другие) по конечным строкам. Проверить `kanban_show`/`runs`; bucket без task ID. |

Пустые/недоступные данные не подменять нулями. | 60 с; `source` (`kanban`, `sessions`, `host`) | Проектируемый сигнал адаптера, в Hermes нет; проверить synthetic fault чтения. |
| `hermes_model_tokens_total` counter-by-snapshot, токенов | `state.db.session_model_usage`: `input`, `output`, `cache_read`, `cache_write`, `reasoning` как отдельные buckets. `reasoning` может входить в output — не складывать с output как дополнительный расход. Это глобально по профилю, не per-Kanban-run. |

Процессы сменяются, PID переиспользуется; соотнесение одного worker с контейнером/проектом требует отдельного идентификатора и измерителя. | По действующему мониторингу; `scope` (`host`, `container`, `process`), фиксированный сервис из allowlist | Гранулярность host/container доступна через существующий мониторинг Tortuga только после отдельной проверки; Hermes Kanban не записывает CPU/RAM/IO по run. Не обещать per-task attribution. |

## Ошибки классификации и границы

1. `blocked` + `needs_input` в ожидании решения владельца — намеренное ожидание; без сведений о согласовании его нельзя объявлять инцидентом. `todo` с несделанным родителем — зависимость; `running` с актуальным heartbeat — штатный прогресс. `rate_limited` означает отдельный сбой квоты/провайдера, не ошибку тестов. Для объяснения конкретного случая смотреть события и runs в Kanban, не пытаться кодировать свободный текст как метку.
2. Единица наблюдения Kanban — карточка/run/event; единица учёта LLM — session/model/task, прямой ключ run→usage в проверенном снимке не обнаружен. Потери, модельные переключения, auxiliary calls и повторные попытки делают деление расхода на карточки неподтверждённым. `pool` не определяет источник оплаты. Отдельно учитывать ресурс времени worker и хоста, но это не денежное списание.
3. Допустимые метки — только закрытые категории из таблицы. Не экспортировать body/comments/event.payload/run.error, логи, сырые чаты, адреса API, токены, файлы клиента; доступ read-only к БД ограничивать на хосте. Для внешнего экспорта/нового сервиса/изменений существующего мониторинга нужно отдельное согласование; этот документ не разрешает запуск exporter или деплой.
4. Дочерняя интеграция `t_2569a694` и корневая `t_cd2d34b0` остаются за собственными gate владельца. Использовать каталог как исследовательский handoff, не как разрешение их разблокировать. После обновления Hermes схема и наблюдаемые статусы проверяются заново.
