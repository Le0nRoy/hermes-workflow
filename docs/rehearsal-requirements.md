## Предложенный учебный заказ

Цель: на изолированном, собственном или разрешённом тестовом приложении «список задач» поставить небольшой воспроизводимый набор API- и браузерных проверок создания и отображения задачи, передать инструкцию запуска и QA-отчёт. Название и контракт приложения — **пример для согласования**, а не утверждение о наличии такого приложения. Если фактический проект другой, сценарии и оценку переписать после обследования, не переносить их механически.

Предполагаемый контракт для оценки объёма (требует подтверждения): тестовая инсталляция с `POST /api/tasks` (JSON `{ "title": string }`, ответ 201 и `{ "id": string, "title": string }`), `GET /api/tasks/{id}` (200 с теми же полями или 404), страница `/tasks` с формой создания, после отправки показывающая заголовок в списке. Для пустого/пробельного заголовка `POST` возвращает 400 без создания записи, форма показывает ошибку. Это **предлагаемая спецификация**, не обнаруженное поведение. Если разработка самого приложения нужна, это отдельный объём.

## Тестовые сценарии (предложение)

| ID | Условия и действие | Ожидаемое наблюдение |
|---|---|---|
| API-01 | На пустой изолированной базе отправить `POST /api/tasks` с уникальным непустым заголовком | 201, JSON содержит непустой `id` и переданный `title`; `GET /api/tasks/{id}` возвращает 200 и тот же заголовок |
| API-02 | Отправить пустой и состоящий из пробелов заголовок | Для каждого варианта 400; созданной записи нет (проверка через согласованный способ чтения состояния/списка) |
| API-03 | Запросить заведомо отсутствующий ID | 404 без неожиданного создания/изменения записей |
| UI-01 | Открыть `/tasks` в согласованном браузере, ввести уникальный заголовок, отправить форму | Заголовок виден в списке после отправки и повторного открытия страницы; сообщение об ошибке отсутствует |
| UI-02 | Отправить форму с пустым/пробельным заголовком | Показана понятная ошибка; в списке нет новой записи |

Предпосылки: адрес тестового стенда, наблюдаемый способ проверки отсутствия записи, текст ошибки и доступные локаторы согласуются с реальным приложением до кодирования. Уникальные заголовки создаются для каждого запуска; уборка тестовых записей или полная пересборка изолированной базы обязательна. Не использовать продакшен, настоящие учётные записи или персональные данные. Если проверка отсутствия записи не наблюдаема через разрешённый интерфейс, API-02 уточнить, а не имитировать доказательство.
