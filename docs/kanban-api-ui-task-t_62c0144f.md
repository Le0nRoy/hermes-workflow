# Учебная API/UI-задача для Kanban — проект постановки

Статус: предложение, не согласованное владельцем задание и не разрешение на запуск. Подготовлено для t_62c0144f как вход в t_9a7b057b; blocked-план t_292e9717 не разблокировать автоматически. Клиентских данных и реального заказа нет.

## Цель и исходные условия

За один демонстрационный цикл получить небольшой, воспроизводимый набор автотестов для локального синтетического стенда заказов `experiments/process-comparison/`: HTTP API из `fixture.py` и автономная HTML/JS-страница `ui.html`. Цель — показать постановку → исполнение → независимую проверку → человеческую приёмку, а не сравнить методологии или опубликовать клиентский кейс. Эти компоненты тематически связаны, но **UI не обращается к API**: сквозной сценарий UI→HTTP→БД в этом стенде невозможен и не входит в объём. Не обещать его в отчёте.

Источник предлагаемого контракта — `experiments/process-comparison/PROTOCOL.md` (разделы A/U); фактические детали сверяются с `fixture.py` и `ui.html`. Это стенд сравнения процессов с известными мутациями, а не согласованный эталон приёмки; повторное использование для Kanban требует решения владельца. Проект пока без HEAD/исходного commit: до первого разрешённого commit фиксировать «commit отсутствует» и хэши файлов; не подменять это выдуманным Git baseline. Изменения продукта, контрольных скриптов `verify.py`/`verify_ui.py`, Tortuga-AI и действующих сервисов не входят в задание.

## Границы и тестовые данные

- API: Python stdlib `unittest`, сервер через `fixture.make_server('clean')`, только `127.0.0.1` и динамический порт, пустое in-memory хранилище на каждый тест, остановка сервера/потока после теста. `POST /orders` принимает JSON-object с непустым строковым `id` и `quantity` целым числом 1..10 (`bool` недопустим); успешный ответ 201 и точный объект `id`/`quantity`. `GET /orders/{id}` — 200 с тем же объектом. Дубликат — 409 без изменения прежней записи, невалидный заказ — 422 без сохранения, некорректный JSON — 400, отсутствующий заказ/путь — 404.
- UI: локальный `ui.html` открывается в новом browser context на каждый тест, без внешней сети и persistent storage. Для 1..10 `Save order` показывает `Saving`, блокирует кнопку до завершения и добавляет ровно одну строку `Quantity: N`, затем `Saved`. Необоснованный повторный клик во время сохранения не должен создавать второй заказ. Вне диапазона — `Invalid quantity` и отсутствие новой строки.
- Только фиктивные `id` вида `demo-<случайный-суффикс>` и количества 1, 10, 3, 0, 11, `true`, строка, `null`, пропущенное поле; никакой персональной информации, реальных транзакций, учётных данных, внешних API или сетевого доступа за пределами loopback. Уникальный `id` на сценарий и новый сервер/context исключают зависимость от порядка и остаточных данных.
- UI-браузер и версии Playwright/Chromium пока не утверждены; предыдущая проверка `verify_ui.py` остановилась на отсутствующем модуле `playwright`. Установку зависимостей, получение браузера и browser-прогон согласовать отдельно. Не считать чтение DOM или наличие Firefox доказательством прохождения Playwright-тестов.

## Ожидаемые сценарии (проект, 8 самостоятельных тестов)

| ID | Действие | Проверяемое наблюдение |
|---|---|---|
| API-01 | Создать заказ `demo-a`, quantity 1; затем GET по id | 201 и точное тело; GET 200 и то же тело. |
| API-02 | Создать заказ quantity 10 | Граница включена: 201, точное тело. |
| API-03 | Подать quantity 0, 11, `true`, строку, `null`, отсутствие поля и пустой id (subtests) | Для каждого 422, заказ не появляется через GET (404). |
| API-04 | Повторить id с другой quantity | 409, GET возвращает исходную quantity. |
| API-05 | Отправить malformed JSON; запросить отсутствующий id и неизвестный путь | 400, 404 и 404 соответственно с контрактными JSON-ошибками; нет побочных записей. |
| UI-01 | Сохранить quantity 1 | `Saving` → `Saved`, одна строка `Quantity: 1`. |
| UI-02 | Сохранить quantity 10 и 3 (отдельные contexts/subtests) | Для каждого одна строка с введённым значением, не подставлено 1. |
| UI-03 | Ввести 0 и 11 (отдельные contexts/subtests); попытаться повторно нажать во время сохранения 3 | Ошибка и отсутствие строк для невалидных значений; после первого нажатия кнопка disabled до завершения, остаётся ровно одна строка. |

Ожидаемые результаты — **требования**, не фактически полученные прогоны. Проверять HTTP status и JSON body, а не только отсутствие исключения; UI — через доступные роли/label и ограниченные ожидания состояний без фиксированных sleep/retry для маскировки дефекта. Вложенные варианты каждого ID явно перечислить в отчёте. Мутации `api-zero`, `api-bool`, `api-duplicate`, `ui-value`, `ui-double` — независимый контроль проверяющего: clean должен проходить, каждая относящаяся мутация должна приводить к осмысленному assertion failure, а не к ошибке импорта/запуска. Контрольные скрипты не выдавать исполнителю как готовое решение; изоляцию доступа к ним организационно согласовать, она не обеспечивается общим UID.

## Готовность к исполнению и приёмка

До запуска владелец явно утверждает: именно этот стенд и 8 сценариев/варианты; место размещения реализации и роль исполнителя/проверяющего; браузер и возможность получить зависимости; источник исходного commit (или разрешение первого commit после проверки состава); объём доступа, разрешённый маршрут модели, квоту/upstream/оплату без платного fallback, ограничение запуска и человеческий gate. Отдельно подтвердить безопасность общего UID/Docker socket: рабочий каталог или Git worktree не являются security sandbox. Без этих решений только постановка, никакой автозапуск тестов или разблокировка t_292e9717.

Приёмка будущей реализации:

1. Таблица ID→путь теста→статус покрывает все 8 сценариев, включая subtests и отрицательные варианты; продукт остаётся неизменным. Независимый проверяющий запускает полный согласованный набор на clean и контролируемых мутациях, записывает реальные stdout/exit и причину падения; infrastructure failure не засчитывает обнаружением дефекта.
2. Проверен второй чистый прогон после полного сброса (новый сервер/context), без зависимости от порядка или повторного использования id. Любой красный clean-тест блокирует приёмку.
3. README реализации указывает версии Python, Playwright и браузера, получение зависимостей по согласованному каналу, команды запуска API/UI по отдельности и полного набора, способ очистки/закрытия ресурсов; независимый повтор по инструкции в утверждённой среде даёт наблюдаемый результат. Если браузерная среда не готова, статус UI — «не проверено», не «успешно».
4. QA-отчёт фиксирует договорённую версию требований, исходный commit либо его отсутствие и хэши, версии среды/модели/скилла, команды, статус каждого сценария и каждой мутации, артефакты, ограничения, измеренные ресурсы и вмешательства человека (`unknown`, если не измерено). Не публиковать секреты, сырые чаты и клиентские данные.
5. Владелец явно принимает результат или возвращает замечания; автоматический green сам по себе не завершает человеческую приёмку. Полный suite и контроль мутаций — ответственность независимого проверяющего; публикация ветки/PR отключена, восстановление/ручной повтор только по согласованному протоколу. Не приписывать Hermes обязанности runner Tortuga-AI автоматически.

Не входят: исправление fixture/UI, flaky-задание, CI, деплой, публикация, новые платные сервисы, внешняя переписка, нагрузка/безопасность, изменение других профилей и работа с Tortuga-AI. Задача пригодна для одного короткого демонстрационного цикла **после** согласования; исполнение и фактические результаты тестов отсутствуют на этапе этой постановки.
