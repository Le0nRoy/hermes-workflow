Нужны решения владельца: число запусков и квотный потолок, разрешённый маршрут модели без платного fallback, разрешение первого commit. Предложение, НЕ решение: один пробный блок из трёх кандидатов на API; затем полная матрица только при подтверждённом остатке квоты. Не запускать дополнительные LLM ради проверки этого пакета. Локальные контрольные тесты не считаются запусками кандидатов.

## Равные исходные условия

1. После UI-проверки заморозить baseline commit и SHA-256 файлов. До разрешения commit использовать приведённый ниже снимок только для локальной проверки, не объявлять его commit.
2. На каждый кандидат × задание × повтор создать новую копию одного baseline. Не переносить решения, историю диалога и логи другого кандидата. Для последовательной работы общий workspace не является security sandbox.
3. Одинаковые: текст задания, входные данные, модель и provider route, разрешённые инструменты, CPU/память, зависимости, тайм-ауты тестов и агентный бюджет. Различается только выбранный процесс. Если разные модели необходимы, это сравнение конфигураций, а не чистый эффект методологии.
4. До первого старта записать версии ОС/Python/браузера/Playwright/Hermes, source commit каждого скилла и SHA-256 всех его файлов, diff адаптации; version model alias не считать неизменным backend. Неизвестное писать `unknown`.
5. Проверяющий хранит verify.py, verify_ui.py, reference_test и матрицу дефектов вне выдаваемой кандидату копии. Кандидату выдавать контракт, clean fixture и стартовый тест (для flaky); оценку запускать отдельно. Скрытие путём инструкции не является изоляцией.
6. Для API: новый make_server('clean') на тест, loopback, динамический порт, свежий пустой orders. Для UI: новый browser context и чистая страница на тест, без сети и persisted storage. Для flaky: новый Job на сценарий.
7. Один writer, последовательно. Не менять действующие сервисы, профили и настройки. Не коммитить, не публиковать ветки/PR автоматически.

## Задание A: API contract tests

Выдаваемый текст:
«Напиши запускаемые автотесты HTTP API заказов, не меняя продукт. Python stdlib, unittest; сервер создавать через fixture.make_server и корректно останавливать. POST /orders принимает JSON object с непустой строкой id и integer quantity 1..10 включительно (boolean не integer). Успех: 201 и точный объект id/quantity; GET /orders/{id}: 200 и тот же объект. Повтор id: 409, исходный объект не изменяется. Невалидный заказ: 422, не сохраняется. Невалидный JSON: 400. Неизвестный путь/заказ: 404. Добавь README с единственной командой запуска; тесты независимы и не требуют внешней сети.»

Приёмка: нижняя/верхняя границы, 0/11, bool/string/null/missing quantity, пустой id, happy path, повтор с отличающимся quantity и последующий GET, отсутствующий заказ, malformed JSON. Проверять status и body, не только отсутствие исключения. Один и тот же набор без правок запускается проверяющим на clean и каждой мутации через подмену фабрики сервера, а не через изменение assertions.
Известные дефекты: api-zero принимает 0; api-bool принимает boolean; api-duplicate перезаписывает заказ. Каждый должен дать assertion failure в относящемся к контракту тесте. Ошибка импорта/инфраструктуры не считается обнаружением.

## Задание U: UI order tests

Выдаваемый текст:
«Напиши Playwright-тесты ui.html. При quantity от 1 до 10 включительно Save order асинхронно добавляет ровно одну строку Quantity: N; промежуточный статус Saving, конечный Saved. Пока операция выполняется, кнопка недоступна и повторный пользовательский click не создаёт второй заказ. Невалидный quantity показывает Invalid quantity и не добавляет строк. Покрой 1, 10, 3, 0, 11 и повторное действие во время сохранения. Используй доступные роли/label, ожидания состояния с ограниченным тайм-аутом, отдельный context на тест. Не меняй продукт, не используй фиксированные sleep/retries для маскировки дефекта.»

Приёмка: реальные browser-тесты, clean проходит; ui-value (сохраняет 1 вместо ввода) и ui-double (не блокирует кнопку) обнаружены независимо. Для ui-double предпочтительна проверка disabled сразу после первого click; негативное доказательство числа строк выполнять после завершения возможных обеих операций. Само DOM-парсирование не заменяет браузер. verify_ui.py — предварительный авторский control, требует выполнения и проверки надёжности до заморозки baseline.

## Задание F: исправить flaky test

Выдаваемый текст:
«Job завершает работу после переменного числа scheduler ticks; result до завершения None, после — saved. Стартовый original_test ждёт ровно два ticks и нестабилен при разной задержке. Исправь только тест: ожидай observable completion с конечным бюджетом, сохрани проверку результата. Нельзя менять Job, отключать assertions, retries, skip/xfail, менять schedule или жёстко подбирать задержку под расписание. Предоставь unittest-набор и команду запуска.»

Кандидату передавать Job, original_test, SCHEDULE из flaky.py, без reference_test и авторского main. Это детерминированная модель timing-flake, не доказательство поведения реального async UI.
Приёмка: сценарии delay=1,3,2,4 проходят; дополнительные delay=0,5 проходят при обоснованном бюджете; never-completing Job завершается assertion failure в конечное время; broken=True по-прежнему падает. Проверяющий прогоняет каждую задержку независимо и проверяет отсутствие неограниченного цикла. reference_test — иллюстрация контроля, не эталон для копирования.

## Процедура и квоты

Предложение полной разведочной матрицы: 3 кандидата × 3 задания × 1 повтор = 9 запусков. Это не статистическое доказательство превосходства. Для повторяемости предложение: ещё один блок = 18 суммарно, только отдельным решением после первого блока. Порядок первого блока: A: Tortuga/make-feature/bulletproof; U: make-feature/bulletproof/Tortuga; F: bulletproof/Tortuga/make-feature. Для повторного блока порядок обратить. Не запускать несогласованный остаток автоматически.

Временный верхний предел из архитектурного handoff: 1800 секунд и 50 итераций на агентный запуск, один ручной повтор. Это не согласованная квота на всю матрицу и не доказательство enforcement. Rate limit, недоступный provider или потеря worker — infrastructure-incomplete; сохранить причину, не засчитывать методологии ноль и не повторять автоматически. Ручной повтор получает новый run_id, оригинал остаётся в отчёте.

До допуска владелец заполняет: approved_runs, approved_route, billing/fallback_policy, available_quota_before, maximum_quota_consumption, stop_threshold, approver/date. Если доступна только грубая индикаторная квота, записать исходный индикатор и источник, не пересчитывать его в токены/деньги. Если квота неизвестна — запуск не разрешён этим протоколом.

## Обязанности вместо Tortuga runner

- Кандидат: решение задания, локальные проверки, отчёт об изменённых файлах.
- Независимый проверяющий: полный suite, clean/mutant runs, оценка known defects, повторяемость и сохранение обезличенного evidence.
- Владелец: human acceptance, разрешение публикации/расхода, решение о ручном повторе.
- Публикация ветки и PR: отключены в этом опыте; не считать выполненными автоматически.
- Восстановление: остановить запуск, сохранить patch и manifest; только разрешённый повтор из чистого baseline. Проверка восстановления worker — отдельный инфраструктурный опыт.
